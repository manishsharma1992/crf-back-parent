Files above; here's the design.**Packages:** `FinancialsResolver` → `application.leverage.ports`. `FinancialTable` → `application.leverage.dto`. `FinancialTableResolver` → `application.leverage.service`, alongside the assembler. No new package needed; you'll still want a `FinancialsResolverImpl` in `infrastructure.leverage`, reading the three columns off the financials row by `financialsId`.

**The central idea is the overlay.** `FinancialTableResolver` produces a small map of dotted keys — `Q-F01.ebitda`, `Q-F01.adjustedEbitda` and the rest — which is merged over the settled answers *before* `FormAnswers` is built. Everything downstream then works unchanged: `fieldValue("adjustedEbitda")` finds it, so Q-Q01 and Q-Q02 can compare; `PreliminaryResponseAssembler` freezes it and stamps `CALCULATED` from `field.isCalculated()`; `QuestionView` renders it. One merge, four problems solved, and no new channel on `FormAnswers`.

**The block is absence, exactly as promised.** When EBITDA or Gross Debt is missing or zero, or Adjusted EBITDA comes to zero, the calculated entries are simply left out of the overlay. The mandatory calculated boxes then have no value, `dataEntryAnswer` returns empty, Q-F01 is unanswered, and semantic #1 stops the walk. No gate, no exception to "traversal is never gated". The sources are still published, so the analyst sees the zero EBITDA that stopped them — and the validation message still fires, because `ValidationDomainService` judges `computed`, not the overlay.

That means the block depends on at least one calculated box being `Mandatory = Yes`. All three totals are in v12, so it holds — but it's a coupling worth a `DecisionTreeValidator` rule later.
